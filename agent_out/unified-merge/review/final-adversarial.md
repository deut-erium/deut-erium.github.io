## Disputed catalog failure handling

Affected:

- If [the catalog entry module](https://github.com/deut-erium/deut-erium.github.io/blob/555ba7a000d63454051b9d20b5b2323e534a978a/new-tetris/src/catalog/index.html#L120) is missing, blocked, or fails before evaluation, the catch never exists. The machine remains safely hidden, but the page stays on "Loading the local square catalog..." indefinitely instead of reporting failure.
- If a later size import rejects, [the click handler](https://github.com/deut-erium/deut-erium.github.io/blob/555ba7a000d63454051b9d20b5b2323e534a978a/new-tetris/src/catalog/catalog.js#L342-L369) does not catch the promise. Blocking the 6x6 data module after a successful 4x4 startup produced one unhandled error, left the machine exposed, retained `aria-pressed="true"` on size 4, and replaced the family list with a permanent loading message.

Checked:

- An initial data-module rejection after the entry module starts is handled correctly. The scoring and game links remain usable in every tested failure state.

Impact:

- The safety gate prevents dead controls during the tested initial failure. It does not provide reliable failure status for entry-module failure or recovery after a later size-load failure. The report's generic "catalog startup failure" wording is therefore too broad.

Fix:

- Give the module script a static error path or timeout that can replace the loading message when the entry module never runs. Catch each size-load promise, restore the last complete state, and announce the failed size without leaving a permanent loading list.
